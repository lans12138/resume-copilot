## FIN-002 第三层根因：expire_approvals 任务本体 async 事件循环 bug（commit ce75cc6）

- run `34806142704`（sha 1dd24e6）仍 failure，但 worker 已正常 ready（`celery@... ready` + `Connected to redis`），队列修复 + 模块形式修复全部生效。任务确实被消费，但 `maintenance.expire_approvals` 运行时崩溃：
  - `RuntimeError: Task ... got Future ... attached to a different loop`
  - `asyncpg.exceptions.InterfaceError: cannot use Connection.transaction() in a manually started transaction`
- 根因两处，都在 `backend/app/maintenance/tasks.py`：
  1. 任务把 async 工作流拆成 **三次独立 `asyncio.run()`**（`_expire` / `commit` / `close`），每次新建并关闭一个事件循环，session 的 connection 跨 loop 复用 → 冲突。
  2. `_resources()` 在**模块导入时**缓存 `RuntimeResources`，其 async engine/redis 绑定了导入时的事件循环；Celery prefork 在 fork 子进程后沿用父进程的 loop 绑定 → 同样跨 loop。
- 修复（commit `ce75cc6`，已推 `origin/main`）：每次 task 调用**新建** `RuntimeResources`，并把 `expire → commit → close session → close resources` 全部放进**单次 `asyncio.run()`**，在同一 loop 内销毁 engine/redis，杜绝跨 loop 复用。任务无候选时仍返回 `{"status":"ok","expired":0}`。
- 待办：run(ce75cc6) 跑完确认 `validate_worker.ps1` 探针转绿（worker 消费 `maintenance.expire_approvals.*succeeded` + beat 发布 `Sending due task...`）。绿则 FIN-002 真正闭合。
- 同模式潜伏 bug（非 FIN-002 阻塞）：`documents/tasks.py` 也是 `_cached_resources` + 多 `asyncio.run()` 写法，后续独立修复。

### 设计：任务即「认领」，不是直接执行

Celery at-least-once + 「不重复执行、不回退终态」⇒ Agent 任务第一步不是执行，而是
`session.get(AgentRun, run_id, with_for_update=True)` 之后问一个**纯函数** `decide_claim(status, cancel_requested, intent)`：

| 意图 | 允许状态 | 其他 |
|---|---|---|
| START | `CREATED` | 终态→跳过；`RUNNING`→跳过（需租约才能区分「已死」与「在跑」，是 FIN-006 的事）；`WAITING_APPROVAL`→拒绝 |
| RETRY | `FAILED` | 其余一律 `NOT_RETRYABLE` |

- **取消标记优先于意图**：`cancel_requested_at` 非空直接 `CANCELLED_BEFORE_START`。
- 行锁持有到「run 到达终态并提交」→ 重复投递阻塞后看到终态，而不是与之竞争；**整趟只 commit 一次** ⇒ Worker 被杀回滚到 `CREATED`，交给 FIN-006 重投。
- `START` **绝不能**接受 `WAITING_APPROVAL`，否则直接违反「未审批副作用执行次数=0」。这也是「`execute_application_run` 必须与 ApplicationRun 路由拆分同批落地」的原因，本轮故意不做。
- 刻意把 RETRY 分支放在终态判断**之前**（`FAILED` 是终态，若先判终态则重试永远进不去）。变异验证：把终态判断前移 → `FAILED+retry` 退化为 `ALREADY_TERMINAL`，测试立刻抓到。

### 新踩的坑：PS 5.1 的 Parser 也是按 ANSI 读文件

## FIN-005 根因第四次纠正：连接风暴，不是快照（commit a86dbc5，已推 origin）

前三次修法（7b96860 rollback+expire_all / f9df127 close / 8789a79+ 工厂 close+reopen）全失败，CI 三轮（34864742879 / 34866789410 / 34868455712）同症「recruitment-flow.spec.ts 0 候选人」。**重新定位**：

### 真正根因 = 工厂模式 close+reopen 冲刷连接池（连接风暴）
`8789a79` 起的 `refresh_for_poll` 每轮询 `await self._session.close()` + `self._session = self._factory()`，把借用的 asyncpg 连接还池又 checkout。DB_POOL_SIZE=5 很小，叠加其它请求 → 连接被频繁 checkin/out；asyncpg 在连接仍疑似有未结事务/结果游标时被还池，GC 以 `garbage collector is cleaning up non-checked-in connection` 回收 → SSE 流在发终态帧前崩（`Exception terminating connection`）。CI 日志铁证：run `8d13f363` 只有一次初始 `GET /match-runs`（200，0 候选人），worker 完成后**无任何第二次 refetch GET**——证明终态帧从未发出，流在 `close()` 处就死了。**不是快照可见性问题**。

### 为什么 7b96860 的 rollback+expire_all 被误判「无效」（重要纠偏）
`7b96860` 当时是 `session=` 单 session 模式，`refresh_for_poll` 有 `if self._factory is None: return` 守卫 → **rollback 根本没执行（no-op）**，快照照冻 → 失败。所以「rollback+expire_all 不重置连接快照」这个结论是**错的**。事实：asyncpg 下 `await session.rollback()` **结束 READ COMMITTED 事务、释放冻结快照**；下一 `session.get` 自动开启新事务，快照即见 worker 提交的 COMMITTED。`expire_all()` 再清身份映射强制重读。两个动作在同一连接完成，**不 churn 池**。

### 修复（a86dbc5）
工厂模式 `refresh_for_poll` 改为：`await self._session.rollback()` + `self._session.expire_all()`（同连接，无 close/reopen）。`aclose` 仍只关这一个 session。配套：重写 `test_sql_repo_refresh_for_poll_recreates_session` → `test_sql_repo_refresh_for_poll_releases_snapshot_in_place`（断言同连接 rollback+expire_all、不关不重开）；更新 repository.py/routes.py 三处 docstring（旧 docstring 声称 rollback+expire_all 无效，已勘误）。

### 结论 + 教学点（最终版，覆盖前面三条错误结论）
- 长生命周期 SSE + SQLAlchemy asyncpg：**绝不要每轮询 close/reopen session**（冲刷小连接池 → 连接风暴 → 流崩）。正确做法是同连接 `rollback()` + `expire_all()` 释放快照并强制重读。
- `rollback()` 确实结束异步事务、释放快照；之前「asyncpg 连接持有快照直到事务结束」的担忧在 rollback 被真正调用时不成立。
- `AsyncSession.expire_all()` 是**同步**方法（只清身份映射，不触发 I/O），调用时**不要 `await`**；`rollback()` 是协程要 `await`。
- 单测守「session 生命周期契约」（同连接 rollback+expire_all），端到端快照可见性仍靠 CI Playwright 兜底。
