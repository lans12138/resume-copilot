**踩到的坑**：镜像里 `tests/` 是 build 时的副本，改完测试不重建镜像跑的还是旧代码。
迭代时用 `-v /d/code/resume/tests:/workspace/tests:ro` + `PYTHONDONTWRITEBYTECODE=1`
挂载，秒级反馈；定版后再 rebuild 验一次。
另外自建脚本要 `PYTHONPATH=/workspace`（镜像 WORKDIR 是 `/workspace`，不是 `/app`）。

### 根因一：种子数据伪造父键

`job_applications` → `jobs` / `candidates`，`jobs` 和 `resume_documents` → `users`，
这些 FK 全是真实且**不可延迟**的，随机 `uuid4()` 填父键必然违规。
修：补真实父行（User / Job / Candidate）。
另外 `uq_job_applications_job_candidate` 限制一对 (job, candidate) 只有一条申请，
所以每条申请要独立的 Candidate。

### 根因二：SQLAlchemy 把环拆错了方向（这个最值钱）

`job_applications` 有一个 `use_alter=True` 的复合 FK 指向 `application_runs`，
而 `application_runs` 又指回 `job_applications` → SQLAlchemy 认为两个 mapper 成环，
拆环时把 **`application_runs` 排在 `job_applications` 前面**，直接撞
`fk_application_runs_application`。
`Approval` 更惨：它跟 `ApplicationRun` 之间没有 `relationship()`，只有裸 FK，
所以**根本没有依赖信息**，被排到第一批，插在父行之前。

实测证据（`echo=True` 看 INSERT 顺序）：
`agent_runs` → `approvals`（job_applications / application_runs 一次都没插）。
注意 `Base.metadata.sorted_tables` 是**对的**，错的是 flush 期的 mapper 排序。

**生产为什么没事**：应用代码分事务写——JobApplication 早已提交，之后才创建
ApplicationRun，两者从不同时处于 pending。测试照做即可：**一层一 flush**。
