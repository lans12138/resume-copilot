### 关键设计决策

1. **过期批处理 = 稳定排序 + SKIP LOCKED**。`ORDER BY approvals.id` 防的是两个 sweeper 候选集部分重叠时的相互等锁；`SKIP LOCKED` 只让第二个 Worker 不阻塞而是继续排空积压。**正确性不在锁上**——认领后必须重读「仍是 PENDING」才迁移，这同时让迟到的 `decide` 自然退化为 no-op。

2. **重投递的 ApplicationRun 分支是本项最危险的地方**。`RUNNING` 静默超 lease 有两种可能：Worker 已死（该救） vs Worker 还活着只是慢（不能碰）。判据是**弃权而非猜测**——只有同时拿到「checkpoint 版本」+「已 EXECUTED 且带 decider 的 Approval」才提议 `RESUME`，否则记 `no_resume_facts` / `approval_decider_missing` 跳过。认领侧还会重校验全部事实与实时授权，所以这个扫描在架构上**只能提议投递**，不可能绕过人工闸门。为此专门写了反向对照测试。

3. **孤儿文件删除顺序**：list → 年龄过滤 → 引用检查 → **再查一次年龄** → 删。中间那次复查是为了防「检查引用期间刚提交的上传」被误删。畸形 key 只计数不删。

4. **单条 broker 失败不致命**：重投递批里单条 enqueue 抛异常只记日志跳过，不 abort 整批（否则一个坏记录会永久卡住后面所有积压）。

1. **重复执行闸门键在 `(dataset_version_id, config_hash)`，与调用者无关**。只看活跃状态（CREATED/RUNNING），`config_hash` 用排序键规范化 JSON 算，字典顺序变化绕不过去。这样闸门不可能被换身份或换键序绕过。

### 关键设计决策

1. **选 `httpx2` 而非官方 `openai` SDK**（用户确认方案 A）。`httpx2` 是仓库既有依赖、运行时可用，自带 `MockTransport`，使整张重试/分类矩阵**无网络、无密钥、无 sleep** 可测；且不必改 `requirements.lock`——本机没有项目生成锁文件的 `pip-compile --no-index` 工具链，改锁文件的风险高于收益。

2. **schema 违例判永久失败**。重发同一请求只会得到同一份畸形回复，判可重试会白白烧掉重试预算。`parse_structured_reply` 里 `CandidateProfileDraft.model_validate` 必须**包在 try/except ValidationError 里**转成 `ChatCompletionShapeError`；漏了这层，坏枚举/多余字段会以裸 `ValidationError` 逃逸，Celery 就会去重试一个注定失败的回调。

3. **抖动只缩不涨**：`[0.5, 1.0)` 而非对称抖动。重试本就是慢路径，不允许把等待拉长到指数之上；同时打散并发 worker，避免重造引发 429 的惊群。

4. **端点脱敏用「整段丢弃」而非「按名猜测」**：query 与 userinfo 全部丢掉。需要猜哪个参数是密钥的脱敏迟早猜错，而这个值是会被打印进工单的。

5. **无法解析的 URL 替换为 `(unparsed)`，绝不原样回显**。手糊进密钥的配置恰恰是最常见的解析失败来源，原样回显就是最不该泄露的那一条。（最初实现回显原文，`test_safe_endpoint_handles_a_malformed_url` 抓到了它。）

6. **录制原始回复文本，而非解析后的 draft**。存 draft 会把本解析器的行为烤进 fixture，也就无法发现解析器后续回归。回放走与线上**完全相同**的解析与校验路径——这才是让回放成为证据而非装饰的原因：fixture 里放一份畸形回复，回放必须失败。

7. **数据集此前从未真正注册**。`register_dataset` 只有测试调用过，生产路径没人调，`dataset_versions` 恒为空、评测结果无法回指数据集版本。`datasets.py` 补上这条接线，并刻意放在独立模块而非路由里，使其可被探针与离线门禁直接调用。
