## FIN-001 修复（follow-up）：SQL takeover_stale 漏 RETURNING（关键教训）
- **提交 `fd0d745` 里 `SqlIdempotencyRepository.takeover_stale` 的 UPDATE 实际漏了 `.returning(...)`**，却用 `result.fetchone() is not None` 判定接管成功。无 RETURNING 的 UPDATE 结果集 0 列，`fetchone()` 永远返回 None → takeover 永远 False → API 重启后的 stale 锁接管失败（follower 撞 max_wait 抛 IDEMPOTENCY_LOCKED/409），破坏验收#4。
- **为何单测没抓到**：`tests/unit` 用的是 `InMemoryIdempotencyRepository`（独立正确实现），SQL 路径只在 `tests/integration` 覆盖，而本机无 PG 跑不了。教训——**InMemory 后端会掩盖 SQL 专属 bug**；凡是 SQL 路径的分支（RETURNING/rowcount/fetchone/方言语法），单测通过不等于 SQL 正确，必须靠真实 PG 集成测试兜住。修复：给 takeover_stale 的 UPDATE 对称加 `.returning(IdempotencyRecord.id)`（与 claim_new 一致），已确认集成测试 `test_sql_stale_lock_takeover_after_restart` 能抓住该回归。
- 复用模式：SQL 判定「本事务是否真插入/接管」一律用 `INSERT/UPDATE ... RETURNING <pk>` + `result.fetchone() is not None`；不要用 `rowcount`（async Result 的 rowcount 在部分方言不可靠），更不要对无 RETURNING 的结果 fetchone()。
